## 一、① 键盘收起不再自动收条

撤的是 `GallerySearchArea` 里那道 `LaunchedEffect(imeVisible)`。立案理由不是"用户不喜欢"一条，
而是它同时压着三件事：

1. 补全是**点一枚即加即重查**，多数输入法会随那次重绘落一次键盘 ⇒ 卡片在用户还没挑完时自己跑掉；
2. 2026-09-29 为它抽过一颗 `GallerySearchCollapse` 挡三种误伤（`imeWasVisible` / `popupOpen` /
   `reverseOpen`）—— 挡到最后剩两种不挡，判据本身已经变成了"这条路的税"；
3. **缺席原因只住在展开区**（`GalleryNotices` 挂在展开那一块里），收条那一刻它整个不画。
   用户 23:39 那张图读到"什么都没发生"，第 3 条是主犯。

收条现在只剩一个触发点：**系统返回**（`GalleryScreen` 的 BackHandler）。展开的入口不变（点卡 / 顶栏🔍）。
键盘仍然参与**高度**判据（`listMaxHeight` 那两档 2/4 行），撤的只是"收条"这一件事。

判据件与它那 4 笔用例整块进 `_trash/gallery-ime-collapse-2026-10-15/`（含 README 与恢复条件）。

## 二、② 整轮失败不再退回首页

`GalleryScreen.kt` 的结果墙接管判据：

```kotlin
// 改前
val searchWallActive = searching && (svm.page > 0 || svm.isSearching)
// 改后
val searchWallActive = searching && (svm.page > 0 || svm.isSearching || svm.searchError != null)
```

成因是纯结构性的：`beginSearch` 把 `page` 归零，而失败路径 `return@launch` **不走** `appendPage`
⇒ `page` 停在 0。第 1 页整轮失败时那把判据当场为假，内容区落回首页那面墙，
而下面那台专门给失败态的空态（"这一轮没搜成" + 条件 + 排行 + 改条件）永远命中不了。

⚠️ **只宽那一处**。同颗文件里另外两道闸门（滚动记录、自动续页）用的是同一串表达式的窄版本，
**故意不改**：`page` 停在 0 时把失败态也喂给续页判据，`runSearch(page + 1)` 就恒等于重跑第 1 页 ⇒
对着一个已知失败的请求无限重发。这条不对称由尺子③的两枚断言一起钉（接管判据里必须有那一支 +
那两道闸门的道数仍是 2）。

`legFailures` 非空**不进**判据：一腿成、一腿败时屏上是有内容的，那一档由页尾与展开区说。

# 第二轮（同日 00:30 · 用户把原文读数带回来了）

## 七、③ 的真凶不是格式，是**月份表问了运行时**

第一轮那一步「把站方原文带上屏」当场生效 —— 用户 00:30 那张截图直接读到了原文
（已归档：`_qa/ui-verify-2026-10-15/scr-00-30-gelbooru-stamp-raw-on-screen.jpg`）：

```
Tue Sep 29 04:45:35 -0500 2026
```

**这一形正是解析器主认的那一种**（六截 Ruby asctime），而 JVM 上的用例还绿着。
差别只可能在月份那一格：

| 侧 | `Month.of(9).getDisplayName(SHORT, Locale.ROOT)` |
| --- | --- |
| 开发机 JVM（本机 `java` 现量 12 枚） | `Jan Feb Mar Apr May Jun Jul Aug **Sep** Oct Nov Dec` |
| Android（`java.time` 走 ICU/CLDR） | 九月是 **`Sept`** |

原实现是拿运行时那份表逐枚比 ⇒ 设备上看 `Sep` 认不出 ⇒ 恒判"读不出日子"。
`minSdk = 33` 且没开 `coreLibraryDesugaring`，所以设备上用的就是平台那套 ICU 数据，
与开发机不是同一份表。

### 用户那句读数把成因钉死了

> 「是年 月 日都有问题，只有全部排行和最新正常」

日/周/月/年**四档都要探边界**，而估点天然落在"今天往回 1~30 天"那一片 = **九月**；
「最新」与「全部排行」不探测，所以照常。四坏两好这一族形状，只有"某个缩写对不上"能造出来。

### 修法

`monthNumber` 不再问运行时，改吃一颗**写死的十二枚表**（`GelbooruWindowBoundary.kt`）：
线上格式不该依赖运行时的本地化数据。`sept` 那一格一并收下（ICU 那侧的写法，零成本）。
两把尺子：

- `everyWireMonthAbbreviationParsesWithoutAskingTheRuntime` —— 十二枚**逐枚现喂**，
  少钉一枚就是三个月后换个坏月再复一次发；
- `monthTableNeverAsksTheRuntimeLocale` —— 负向尺，扫代码行禁 `getDisplayName` / `TextStyle` /
  `java.time.Month`，**自带对照组**（自己喂一行被禁的 import 进去，必须抓得住）。
  只测"十二枚都过"挡不住有人三个月后把实现改回去 —— 那一改在开发机上照样全绿。

## 十一、⑤ 的连带效应：尺寸要**分开**

用户：「最近搜索的按钮设计大点，连同搜索 tag 一起变大了，你分开」。

第二轮那版是"removable 一律给 40dp 命中盒"，于是**已选条件那一排胶囊跟着长高**
（同一枚 × 住在两种容器里：历史那一条是**要按的按钮**，条件胶囊是**一排里的一个元素**，
而那一屏每一行都在抢卡片高度）。

改法：`VeneraChip` 多一枚 `removeTouchSize: Dp?`，**由住它的那一处表态** ——

| 调用点 | 给的那一档 | 结果 |
| --- | --- | --- |
| `HistoryList`（最近搜索） | `tokens.spacing.iconButtonSize`（40dp） | 命中区 256 → 1600dp²，整枚 ≥48dp |
| `FilterChipItem`（已选条件） | **显式写 `null`** | 逐字退回第二轮之前的形状（× 的 clickable 仍在图标上） |

为什么不用编译器强制必填：这颗组件有二十来处调用，全改成必填只会逼出二十行无意义实参。
所以换成一把**道数尺**：`onRemoveClick` 与 `removeTouchSize` 在 `GallerySearchArea` 里必须**数量相等**
（今天都是 2）—— 新增第三处 removable 却没表态，当场红。

## 十二、⑥ 搜索卡挡图：按用户选的"收窄 + 透底"，不动避让几何

用户选的解法是**还是浮层，但收窄 + 透底**。这一格刻意**没有**去给网格加顶部避让：
那条"padding 随滚动状态变"的通道 2026-09-30 撤过，撤的理由至今成立 —— 卡片收放时 padding 一变，
整面墙会跳一下（`gridTopPadding` 那颗 val 的头注写着这段历史）。

| 档 | 宽度 | 底色 |
| --- | --- | --- |
| 展开（INPUT） | 满宽（不变） | `surfaceContainerHigh` 实色（不变） |
| 收成一条（RESULTS） | `widthIn(max = 屏宽 × collapsedChipWidthFraction)` | 同一颗色 `copy(alpha = tagContainerAlpha)` |

两个数都是**现成的**：`collapsedChipWidthFraction` 就是下滑之后顶栏那行吸附胶囊用的同一把宽度尺
（同一件事在两处只许一把尺子），`tagContainerAlpha = 0.90` 是封面标签那一档
"是容器但仍透出背后"。展开态**留在实色**：那一态下面压着键盘与补全，没有"图被挡住"这件事，
透底只会让字更难读。

## 十三、Gelbooru 的「选哪一期」为什么开不了（用户问的）

> ⚠️ **本节的结论已被同日 §十五 推翻**（2026-10-16 带凭据现量）：上界探得出来，历史期已经能选。
> 下面这段留着，是因为"站方不认区间语法"这条仍然成立 —— 错的只是本鱼当时把它读成"框不住"。

不是漏接线，是**拼不出上界**：

- 站方 DAPI 只认 `id:>=A` 这一枚下界；区间写法 `id:A..B` 与 `id:A..` 都被**静默忽略**
  （`count` 与全站逐字相同 —— 2026-10-13 带凭据现量，见 `GelbooruWindowBoundary` 头注）；
- 所以合成档那一串是 `id:>=A sort:score:desc`，**终点靠 id 单调性自然兜住** ——
  本期没问题（上界就是今天），而"2026-03 那一期"框不住：发出去会变成"3 月起到现在"；
- 判据因此把 Gelbooru 的日期弹层整档关掉（`supportsPeriodPicker(GELBOORU)` = false，
  定义挂在 `supports(site, MONTH)` 上），菜单里那一行「选具体哪一期…」就不出现。

**要开它需要什么**：一次带凭据的现量，问 `id:>=A id:<B`（两枚独立标签，不是区间语法）
到底过不过滤 —— 判据用 `count`：与只给下界时**相等**就是被忽略。本机量不到（匿名一律 401）。
可以按"探测 + count 自检 + 定不出来就不发"那套现成形状接进去（与起点定界同一个纪律，
失败不会长成假开关），但**要不要花这一笔**由用户点头：它换来的是 Gelbooru 能翻历史期，
代价是每一档多几笔 `limit=1` 的探测。

## 十五、§十三 那一格被推翻了：闭环窗口（起 + 止两枚边界）落地

用户直接把凭据贴进对话：「凭证给你，你自己测下到底能不能获取到具体到 x 月 xx 日 xx 年」。
测完的答案是**能**，于是按用户那条口径（「行的话就直接加吧」）当场接进去 —— §十三 那一段
写的"要开它需要什么"从今天起是历史。

**站方语法（现量，`_qa/gb_range_hunt_ledger.txt`）**

- `date:` 仍然 `count=0`（这一条没变）；
- 区间写法 `id:14718000..14994000` 仍被**静默忽略** —— 与全站基线**逐字相同**；
- 两枚独立标签生效，且是**可减的**（这一步是整个判断的凭据，不靠眼力）：
  基线 `count=14,426,357`；`id:>=14718000` = 375,233；`id:>=14994000` = 101,393；
  两枚同给 = **273,840 = 375,233 − 101,393**；另 `id:<14994000` = 14,324,964。

**真正的难点不是语法，是成本**：老的估点只有一颗 `IDS_PER_DAY` 常数，拿去问历史期，
2024 那一页要 14 笔探测（≈21 s）、整年要 27 笔（≈33 s），而单腿预算是 12 s ——
"问得出来"和"点得动"之间差的不是代码是一张表。

**落地五格**

1. **烘焙进源码的 id↔日期校准表**（`GelbooruWindowBoundary.CALIBRATION`，19 行 = 每年年初那枚 id，
   不可变的历史事实）；估点与跳距都改吃**分段插值**：2026 段斜率 6,532/天、2024 段 4,927/天。
2. **候选顺序**：从最近那枚已知读数走割线 → 绝对插值 → 目标日退一天 → 中点，
   且只收**严格落在括号内**的候选。割线在括号跨一天时会退化（台架烧掉 18 笔一路爬
   `high-1、high-2` 就是这个形状），退化即切中点。
3. **收口方向不对称**：窗口起点落在 `high`（少一条是看得见、也不会错拿别期的那一侧），
   窗口终点落在 `low + 1`（绝不把下一期的头一条算进来 —— 那是本仓"宁可错慢不可静默交错"那一族）。
4. **开放结尾是一种结论不是失败**：终点那一趟探到 `TopReachedWithoutBracket` = **证明这一期没有上界**
   ⇒ 交回 `GelbooruWindowEnd.Unbounded`，发出去与"本期"那一档逐字相同。`null` 会把"不需要上界"
   与"没定出上界"混成一格，所以立了 `GelbooruWindowEnd` 这一枚类型。
5. **腿预算分档**：单边界（本期）仍 12 s；两边界（历史期）`CLOSED_WINDOW_LEG_TIMEOUT_MS = 30_000L`。
   两枚边界**共用一份读数**（第二趟带着第一趟的 readings 起步），但**共用同一笔预算**。

**顺带抓到一条真·假开关**：`pickPeriod` 的门用的是**桌面**那把判据（`supportsPeriodPickerAll`），
而菜单里那一行用**移动端**那把（`supportsPeriodPickerForApp`）⇒ 行会出现、按下去什么都不发。
已改成同一把，并加负向尺整树禁 `gallery/ui/` 再出现桌面那把名字。

**现量成本**：历史月档 11 笔请求 ≈ 10–12 s 出图，第二次点同一档命中缓存瞬时（`_qa/gb_tr4.txt`）。

## 十六、真机第四轮：那一片空位在右边，所以那一行挂右
