### 5.2 判据先红抓到的那枚真缺陷：枚数乘法在 `Int` 里绕回

台架 P1–P10 逐笔咬住之后做了一次"哪些判据没有笔"的自审，量到**上限分支零覆盖**（`desktopDecoDotTileForArea` 没有任何笔碰过）。
补的那颗判据（`点数触顶时步长成倍放大而乘数封顶三十二`）**在干净树上就红了**，不是笔写错：

```
面积荒谬（1e9 见方）时停在 11×32 而不是继续乘 —— expected:<352.0> but was:<44.0>
```

- `44 = 11 × 4` ⇒ 那条 `while` 在乘到 4 倍时就认为"已经压进上限了"。真原因是 `desktopDecoDotCount` 写成
  `Int * Int`：两轴各 `⌊1e9/11⌋+1 ≈ 9,090 万` 枚，乘积 ≈8.3e15 远超 `2^31` ⇒ **绕回成一个小数**，上限判据拿到的是那个小数。
- **今天递不进这么大的面积**：唯一的调用点递的是 Canvas 的 `size.width/height`（窗宽几千 px ⇒ 单轴 ≈4,400 枚、乘积 ≈1,900 万，
  离溢出还差 100 倍）。所以这不是一枚用户已经踩到的崩，而是一枚**"上限只是写着好看"**的静默失效 —— 那一族本仓忌得最狠。
- 修法（最小）：两轴各自 `toLong()`，乘积超过 `Int.MAX_VALUE` 就**钉在 `Int.MAX_VALUE`**。方向选"宁可多算"而不是"宁可少算"：
  多算 ⇒ 荒谬面积上把步长再放大一档（画得稀一点）；少算 ⇒ 真画几万枚点、卡在绘帧线程上。
- 复现笔 = **P23**（把两行 `toLong()` 改回 `toInt()`），它同时也是"这颗判据真的咬得住溢出"的证据；
  另两枚上限笔各咬另一件事：**P18** 拆掉整个放大支（②③ 一起红），**P19** 只拆 `multiple < 32` 那道乘数上界
  （真实窗宽下行为完全一样 ⇒ 只有 ③ 那格露馅，这一枚存在的理由就是它证的是尺子而不是行为）。

这条正好把既有纪律「自适应分支的新依赖面要查退化输入(0/负/**溢出**)」从散文兑成了判据。

### 8.4 画法：樱走四段贝塞尔，玉走 SVG 端点式弧的圆心推导

- **五瓣樱**（稿 `:322`）：模板是 `ellipse cx=8 cy=4.4 rx=2.5 ry=3.4`，五枚各绕花心 (8,8) 转 `i×72` 度。
  Compose 里没有"旋转的椭圆"这一枚原语，所以把椭圆拆成**四段三次贝塞尔**（系数 `ELLIPSE_KAPPA = 0.5522847498`），
  再把模板点集绕 (8,8) 做一次相似变换。本批没用 `DrawScope.rotate`——判据要能**直接吃同一条算式**
  （`desktopSakuraPetals()` 给出那五枚的方位，而画法吃它），中间隔一层库的变换就成两份答案。
  ⚠️ 顺手记一条量具边界：`javap` 读 `androidx.compose.ui.graphics.drawscope.DrawScope`（桌面 1.12.1）
  时 `rotate/scale/translate` 三颗**一行都没列出**（现量 0 行），但这一条**不作为"桌面上没有它"的负结论**——

- **阴阳玉**（稿 `:321`）：`M8 1.6a6.4 6.4 0 0 1 0 12.8z` 是**端点式**弧。弦长 11.2 < 直径 12.8 ⇒
  那条弧所在圆的圆心**不在 (8,8)**，而在弦的中垂线上、距中点 `sqrt(6.4² − 5.6²) = 3.0984`；
  `sweep=1` 取左边那一枚 `(4.9016, 7.2)` ⇒ 小弧往**右**凸，那片白是一块**弓形**（右缘 11.3016）而不是半圆。

  `arcCenterX < 8`、`起点/终点落在那条弧的圆上`、`右缘 = 11.3016` 这三件事，而不是"看着像"。
- **判据不吃 Path 包围盒**：贝塞尔与圆锥曲线在 Skia 的 `getBounds()` 里是**含控制点的保守盒**
  （控制点本来就跑到曲线外），所以樱的角度/半径钉在 `desktopSakuraPetals()` 的参数上，
  玉的凸向钉在 `desktopGyokuShape()` 的参数上；盒宽盒高只对**未旋转那一枚**用了（那时四个锚点恰在盒边上，保守盒 = 真盒）。
