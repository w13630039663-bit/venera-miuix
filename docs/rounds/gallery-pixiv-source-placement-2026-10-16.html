画廊接入 pixiv：入口形态方案

范围：只谈 app/ 手机档的信息架构与入口形态。未动一行代码，本文是方案稿。

依据：gallery/ui/* 与 ui/tokens/* 通读 ＋ 用户 2026-10-16 提供的画廊首页真机截图（1080×2376）

一句话结论：建议「分区」，不建议「混成第四站」。

不是审美偏好，是一条算出来的硬约束：现在那一排来源分段器实得 337dp，4 格时每格文字可用 56.8dp 已经在临界； 加到 5 格掉到 39.4dp，三个拉丁站名全部进省略号（§二 有完整推导）。 而 pixiv 与 booru 的差异不只是"多一个站"，是搜索语法、分级字形、排行档三套语义全都不同 —— 硬塞进同一条来源轴，会让「全部」这一档变成一句读不出对错的假读数。

分区之后，两个世界的轴各自自持，而分段器永远回到今天已经验收过的 4 格密度。

2026-10-16 现量改判（本文件下面三处结论已过期，原文保留不删）

① §三 的位置不成立：来源轴今天不在 chrome 下面，它长在展开的搜索卡里 （gallery/ui/GallerySearchArea.kt:778），首页那一排 2026-10-15 已被点名摘掉 （gallery/ui/GalleryHomeChrome.kt:51-67「顶栏下因此永远不会同时出现两套来源切换器：只有一套，长在卡里」）。

② §一 的档名是错的：匿名 JSON 认的是 daily/weekly/monthly/rookie/original/male/female， 而 day/week/month 回 404「ランキングが見つかりません」。

全站放法调研与端点状态表：docs/rounds/gallery-pixiv-placement-options-2026-10-16.md。 用户 2026-10-16 另给了一张新示意（搜索框下面三格「综合 / 图库站 / Pixiv」），它落在内容层第一行， 三把尺子（66dp 常量、卡内分段器计数、收栏阈值）一个字都不用改。

二、硬约束：那一排分段器已经装不下了

这一条是算出来的。VeneraSegmentedButton 自己不定宽（组件头注："整条宽度仍由调用方推导"）， 而搜索卡里那个调用点传的是 fillMaxWidth() —— 所以每格宽度由真实的 padding 链决定，不是屏宽除以格数。 把链子走一遍（截图 1080px 宽，按密度 2.75 折 ≈ 393dp —— 密度这一项是假设， 但仓内多处注释引用的正是 393dp 参考机，且下面的结论只依赖"337dp 实宽"这一个相对量，不依赖绝对值）：

环节来源剩余宽
屏宽393dp 手机档393dp
搜索卡外层左右内缩screenHorizontal 12dp × 2369dp
卡内那一列左右内衬space8 16dp × 2337dp

也就是分段器实得 337dp。再扣掉格间 segmentedGap（10dp）与每格内部文字左右各 space5（10dp）：

格数格间占用每格总宽文字可用宽结果
4 格（今天：全部 / yande.re / Gelbooru / Safebooru） 3 × 10 = 30dp 76.8dp 56.8dp 已到临界 "Safebooru"（9 字符）就在边上
5 格（＋ pixiv） 4 × 10 = 40dp 59.4dp 39.4dp 掉 31% 三个拉丁站名全进省略号
关于字宽的诚实标注：上面"每格总宽 / 文字可用宽"两列是从 token 精确算出的（12、16、10、10 都是源码里的确定值）； 而"某个站名要多少 dp"是按 14sp 拉丁字均宽估的，本机没有设备量过。 但结论不依赖那个估算 —— 文字可用宽从 56.8dp 掉到 39.4dp 是确定的， 而任何一个 8~9 字符的拉丁站名都不可能塞进 39dp。所以 5 格必然大面积省略号，这一条成立。

更糟的是宽屏档：isWideScreen（>600dp）会把高度升到 segmentedHeightWide（56dp）、 字号升到 itemTitle（MD3 16sp / MIUIX 17sp），字更大而格数不变 —— 平板上 5 格崩得比手机更早。

三、三个方案

图 2 · A 是"多加一格"；B 是"多一层分区，两边的轴各自自持"。卡片墙三者都不用改。

方案 A · 混成第四站

好处

  • 改动最小：GallerySearchSource.options 自动多一格，「全部」自动包含它
  • 与现有「一次打多站」的心智完全一致
  • 收藏 / 历史 / 关注那些存储**天然不用动**

代价（前两条是致命的）

  • 分段器三格变省略号（§二已量）
  • 「全部」这一档变成假读数：同一串条件打四站，pixiv 那腿的 order:score 会被当搜索词、排行档两边交集只有三个 —— 胶囊上写「周」，实际有一站按别的口径出的图
  • 要额外加第三套分级字形 + 第三套排序后缀，全塞进已经有两个特例分支的 GalleryRankings

方案 B · 分区（推荐）

在 chrome 下面加一层两格的分区选择器，它决定第二排是哪一根轴：

分区 = 图站分区 = pixiv
第二排（轴）全部 / yande.re / Gelbooru / Safebooru
4 格 · 今天已验收		日榜 / 周榜 / 月榜 / 新人榜
4 格
搜索语法tags=… order:scoreword=…&sort=…&mode=…
「全部」的含义三个 booru 的并（语义同源，合并成立）不摆这一档 pixiv 自己就是一站，没有"并"可言
分级沿用现有两套字形新增 xRestrict/sl 一套
排序后缀GalleryRankings.suffix() 现有分支走 pixiv 自己的表

好处

  • 两根轴各自自持：两边的排序档、语法、分级都不互相污染
  • 分段器回到 4 格，也就是今天已经在真机上验收过的密度
  • 两格的分区选择器每格 ≈163dp（同样 337dp 实宽下 (337−10)/2），怎么写都不会省略号
  • 「全部」这一档的语义重新变真：它只并同源的三个 booru
  • 将来 pixiv 若要上鉴权（关注 / R-18），影响面被关在第二排之内

代价

  • 多一层。第一排两格 + 第二排四格 = 两排控件，比今天多占一层的高度。 具体多少取决于第一排用哪一档：走 VeneraSegmentedButton（segmentedHeight 48dp）＋ 行距 ≈ 56~58dp； 走 chip 那一档（filterChipHeight 32dp）≈ 40~44dp。方案稿里画的是后者。
  • GallerySearchViewModel.source 要变成"分区 + 轴"两段状态（换分区 = 换一轮上下文，与现有"换来源=换一轮"同一条判据）
  • 首次进入要有个默认分区（建议默认「图站」，不改变老用户观感）

关于那多出来的一层高度

可以用把分区选择器折进 chrome 那一行来省掉：chrome 右边那枚反搜入口挪进搜索卡， 腾出来的位置摆一个两格的小分段器。这样净增高 ≈ 0。但那一行是定高件 （galleryHomeChromeHeight() = space2 + 56 + space3 = 66dp，且与收栏阈值有硬耦合、有用例钉着）， 动它要同时改常量与 GalleryHomeChromeTest。建议第一版先老老实实摆两排，真机看过再决定要不要折。

方案 C · pixiv 独立成第六个 Tab

好处

  • 隔离最彻底，画廊那一屏一行都不用改

代价

  • 底栏今天 5 格（VeneraNavTab.entries：首页/收藏/搜索/画廊/探索）。6 格在 393dp 上每格 ≈61dp，图标 + 文字挤
  • 加一格要动 tabIndex / currentTab / hasRoute 三处映射 + 底栏那套物理回弹指示器
  • 底栏是最贵的常驻位置，为"第四个图源"占一格不划算 —— 它本该留给"另一类内容"
  • pixiv 与画廊共用卡片墙、收藏、历史、画师页，拆成两个 Tab 会让这些共享件出现两份入口

四、推荐：方案 B，分三步走

步做什么为什么先做它验收
B1 只加分区选择器 + 两根轴，先不接 pixiv 的网（第二排先摆假档，或整块隐藏） 先把"多一层"这件事在真机上量掉：高度、收栏阈值、与 chrome 的关系。这一步零网络风险 真机截图：两排控件的间距、滚动时收栏是否还正常
B2 pixiv 只进排行 + 搜索，不进日榜混合墙 用户显式选了 pixiv 才发车，影响面最小；分级与多页建模可以在这里单独验 pixiv 那一区出图、卡片分级正确、页尾读数对
B3 真机验过之后再考虑进「每日热门」混合墙 混合墙会把四站各抽 20 洗成 80 张一屏，错了就是整屏内容不对 首页混合墙里 pixiv 卡片比例正确、无 ugoira 黑卡

为什么不建议一上来就做 A：A 的"改动最小"是真的，但它把两个成本藏到了后面 —— 分段器崩掉是立刻可见的，而「全部」这一档的语义污染是静默的： 用户选了「周」，屏上四站的图都有，而他读不出 pixiv 那几张其实按别的口径出的。 本仓对这类"读不出对错"的形态一贯是零容忍，所以宁可先多一层。

五、几个待你拍板的点

#问题我的建议
1分区选择器的默认档是「图站」还是「pixiv」？图站。默认档不该改变老用户的观感（与"全部作为默认档"那次拍板同一条理由）
2分区选择器折进 chrome 还是单独一排？先单独一排。折进去要动定高常量与它的守卫用例，等真机量过高度的代价再说
3pixiv 那一区第二排摆排行档还是搜索？摆排行档（日/周/月/新人）—— 它是"打开就有内容"的那一档；搜索走 chrome 那条，两区共用
4多页作品（一条 illust 几十页）在卡片角要不要标「12 页」？要标。否则点进去才发现是组图，与"点开看到 12 张"的预期不符
5ugoira（动图）在卡片上怎么表达？沿用现有视频角标那一套（durationLabel 那条），但**先不播** —— 点开给首帧 + 一句"暂不支持播放"

六、明确不做

  • 不动卡片墙。三个方案的墙都一样，pixiv 卡片复用现有 GalleryCardsGrid。
  • 不做第六个底栏 Tab（方案 C 的理由见上）。
  • 不把 pixiv 塞进「全部」。哪怕将来做 A，也不该让「全部」包含一个语法不同的站。
  • 不在第一版做鉴权（关注 / 书签 / R-18）。匿名已覆盖浏览 + 搜索 + 排行，鉴权带进来的是凭据存储、刷新失败、账号风控三件长期负担。
