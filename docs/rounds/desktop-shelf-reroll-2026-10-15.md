# 第一百一十三批方案 · 「补齐」跑完之后，那一屏那一行为什么还念「缺 2 页」

日期：2026-10-15 ｜ 前置：批 111（rounds `desktop-shelf-repair-handle-2026-10-14.md`）+ 批 112（rounds `desktop-shelf-raw-id-2026-10-15.md`）
本篇要动的域：`desktop/src/main`、`desktop/src/test`、`_qa`（`app/` 一颗不碰）

## 0. 题面（两处读数 + 一处代码原话，都不是推断）

批 111 给「缺 N 页」那一行装了「补齐」把手，批 112 让它排的是**原号**。但那一屏按完之后**不会自己改口**：

- 代码原话：`DesktopComicDownloadsPane.kt:106-112` 那颗 `fireRepair` 里排完队就 `pass += 1`，
  而 `pass` 是 `LaunchedEffect(downloadsRoot, pass)`（`:72`）唯一的推进器 ——
  也就是说**重数发生在「入队那一刻」**，那一刻盘上还是 28 页，重数出来的还是「缺 2 页」。
  真正改了盘的那一跳（泵跑完、页落盘）**没有任何东西去推 `pass`**。
- 更要命的是同一颗文件 `:103` 那句注释写着「重数一遍是为了让那一行的『缺 N 页』跟着补完的结果自己改口」——
  **注释把意图写成了事实**，而事实是它跟着"入队"改口（什么也没改）。
- 包内读数（2026-10-15，`_qa/desktop-exe-2026-10-15-b112/run-raw-a.log`）：
  ```
  D_补齐种子 … 缺=2 留=28 排队=是 · 号按本机记录还原成 /manga/pandajunheleisajun-hiyaku
  D_本机下载 本=1 话=1 齐=0 缺=1 跳=0 字节=2655958      ← 入队那一刻的重数（盘上还是 28）
  D_下载进度 … 页=28/30 → 29/30 → 30/30
  D_下载 … 页=2/30 全=是                                ← 补齐真跑完了
  （此后再没有一行 D_本机下载）
  ```
  ⇒ 用户在那一屏看到的是「缺 2 页」+ 一枚还能按的「补齐」，而盘上其实已经 30/30。
  这是**第一帧假话**那一家（批 105 记过两格）的第三格，方向相反：不是读早了，是**该重读的时候没人推**。

同族的另一格：批 98 的删除那一路是**同步**改盘的（`desktopComicDeleteChapter` 返回就是删完了），所以那里 `pass += 1` 是对的；
补齐那一路是**异步**的（入队 ≠ 落盘）。两路同一个动作名、两种时机 —— 本批只改异步那一路。

## 1. 定档

**只加一枚"什么时候该重读盘"的判据，不改那一屏的读侧**：
新建纯件 `desktopComicShelfRerollKey(tasks)` —— 把队列里**终局那一档**的三枚计数拼成一串
（`完=n 败=n 停=n`）。屏上把它当 `LaunchedEffect` 的一枚键：

- 一笔从 `RUNNING` 落到 `DONE` / `FAILED` / `STOPPED` ⇒ 串变 ⇒ 那一屏重读盘 ⇒ 那一行自己改口；
- 一笔还在 `PENDING`/`RUNNING` 里逐页刷 `downloadedPages` ⇒ 串不变 ⇒ **不去读盘**（每页刷一次盘就是 批 110 那把尺子中每一颗文件的头部读一遍，纯浪费）；
- 入队那一刻不再 `pass += 1`（盘上什么都没变，重数出来的还是同一句假话）。

- ⚠️ 不许轮询（批 108 立的那条）：推进器是 `StateFlow` 的订阅（`collectAsState`），不是 `delay` 循环。
- ⚠️ 组合期仍不读盘、不读队列内容当**展示数据**：屏上那些行仍然只从 `state`（读盘那件）来；
  队列那一头只贡献"何时再读一次"这一枚键。批 112 的 ⑥⑦⑧ 三颗（回收只在要用的那一刻现读）不许回流。
- 为什么按"终局计数"而不是按"这笔任务的 taskId 到没到 DONE"：那一屏不知道用户按的是哪一笔，
  而 `补完任何一笔` 都意味着盘上多了东西 ⇒ 计数够硬且不牵动行模型。
