## §1 第 3 条：上下滑收栏没效果 —— 根因

`GalleryScreen.kt:303` 那枚 `NestedScrollConnection` 挂的是 **`onPostScroll`**，读的是 `available.y`。

Compose 的 post-scroll 语义是"**子级消费完之后剩下的那一截**"。首页那面瀑布流只要还能滚，
它就把整笔位移吃干净 ⇒ 到达这一层的 `available.y` **恒为 0** ⇒ 判据每帧拿到 `delta = 0`：

- `delta < 0f` 不成立（不走"立即展开"那一路）；
- `accumulated + 0 >= threshold` 永远不成立 ⇒ **永远不收**。

唯一能产生非 0 `available.y` 的时机是"已经滚到底、手指还继续往下推"，日常滑动碰不到。
而反方向是通的：在顶部往上推时子级吃不下，`available.y < 0` ⇒ 每帧都返回"展开"。

**所以屏上的表现正好是"只会展开、从不收起"= 用户说的"没有效果"。**

第二处成因（同一枚连接上）：它现在挂在 `topBarBehavior.nestedScrollConnection` 的**外面**
（`.nestedScroll(chromeHide).nestedScroll(topBar)`，链上**靠后的更贴近子级**）。
miuix 顶栏折叠在 pre 段就把位移吃掉，等传到这里已经所剩无几 ⇒ 就算改成 pre 段读，
也要等顶栏完全折平之后才开始累计。

### 修法（判据层一行不改）

- 改读 **`onPreScroll`** 的入参 `available.y`：那才是这一笔的真实位移（正 = 手指向上推内容 = 下滑，
  与 `GalleryChromeHidePolicy` 注释里的符号口径一致）。
- 把这枚连接挪到**最内层**：`.nestedScroll(topBarBehavior.nestedScrollConnection).nestedScroll(chromeHideConnection)`。
  它恒回 `Offset.Zero`，不抢任何位移，所以"谁先看到"就决定了"谁拿到的是原始值"。
- `GalleryChromeHidePolicy`（含 8 条单测）**不动**：符号与阈值口径都没变，变的是取数位置。

### 这轮证明不了什么

根因是**读码结论**，不是实测读数。改完要靠真机验（§8 清单第 1 条）：
下滑过搜索框位置 → 两栏各自按开关收起；上滑任意幅度 → 立即展开；双击回顶 → 复位。

## §2 第 6 条：`img.pixiv.net` 出处时有时无 —— 根因（有实测数）

判据层把 pixiv 的**图床子域**一律判成 OTHER（`GalleryArtistLinks.isPixivImageMirror`，
认 `^(img\d*|i\d+)$`），`pixivArtworkId()` 对同一批 host 直接 `return null`。
那条口径本来是为"站方把 `img42.pixiv.net/img/tehu48/` 这种**目录列表**登记成个人主页"立的，没错；
错在把**带作品号的裸图**一起挡掉了。

2026-09-30 实测（`curl -x http://127.0.0.1:7890` 取 yande.re `post.json?limit=100` + 设备 `gallery_feed_cache.json`）：

| 出处形状 | 条数（yande.re 100 条里） | 现在的判定 |
| --- | --- | --- |
| `www.pixiv.net/artworks/150280791`、`/en/artworks/…` | 26 | 认出作品号 → 反查作者 → **能显示** |
| `i.pximg.net/img-original/img/2026-09-30/…/150281277_p0.jpg` | 8 | **认不出** |
| `http://img.pixiv.net/img/…`（老式，用户截图里那种） | 本批 0，历史池里有 | **认不出** |
| `x.com` / `baraag.net` / `www.fanbox.cc` 等 | 其余 | 各走各的既有口径 |

"认不出"的那批只有在这帖**恰好带站方画师标签**时才有画师信息 ⇒ 用户读到的就是
"同一类出处，有时可以显示有时无法显示"。

### 修法

裸图 URL 的**文件名里本来就带着作品号**（`<illustId>_p<页>.<扩展名>`）。
所以只需放宽 `pixivArtworkId()`：host 是 pixiv 图床子域（`i.pximg.net` / `img*.pixiv.net` / `i*.pixiv.net`）时，
从路径最后一段取 `(\d+)_p\d+` / `(\d+)_bigp\d+` / `(\d+)_ugoira\d+` 里的那串数字当作品号，
后面接的反查（`PixivClient.artworkAuthor` → `ajax/illust/{号}`）**已经跑通，一行不改**。

仍然不认的：`img42.pixiv.net/img/tehu48/` 这类**没有作品号的目录串**（那条旧口径继续有效）。

`fromSource()` 保持不变 —— 裸图**不是**"这个人"的主页，不能直接当入口摆；
它只是"要不要多花一笔反查请求"的闸门，反查回来的 `users/{id}` 才是入口（且照 L10 口径带账号）。

## §3 第 2 条：撤下拉刷新 + 换一批只刷推荐区

### 3.1 撤下拉刷新（两层都撤）

用户说的是"整个画廊"，所以两层 `PullToRefreshBox` 都换成普通 `Box`（各自的 `nestedScroll` 链保留）：

- `GalleryScreen.kt:848`（首页主墙）；
- `GalleryDailyScreen.kt:127`（每日热门二级页）。

撤了之后"我要新内容"的出口还剩两枚，都是真按钮：猜你喜欢节头的「换一批」、二级页顶栏的「换一批」。
这与 2026-09-29 第四轮加下拉刷新时的理由（"同一天之内不再自动联网，得有个说得出口的动作"）
并不冲突 —— 那个动作现在由「换一批」承担。

### 3.2 换一批不再整页刷新 —— 根因

`GalleryForYouViewModel.refresh()`（:278）会 `posts = emptyList()` + `stage = IDLE`，
于是 `GalleryForYouPage:81` 那一档（`IDLE || (isLoading && posts.isEmpty())`）命中，
**整屏**换成一个居中波浪环 ⇒ 三节（正在关注的画师 / 每日热门 / 猜你喜欢节头）跟着一起消失。
这就是"整个页面刷新"的观感来源。

### 3.3 修法（拍板：保留上一批 + 压一层轻指示）

- `refresh()` **不再清空 `posts`**（其余字段照旧清：seed / page / stage / seenKeys / failures …），
  让上一批卡片留在屏上；
- `GalleryForYouPage` 那个"整屏波浪环"档只在 **`posts` 真的是空的**时候才命中（冷启动第一轮）；
- 重取期间在墙上压一层轻指示（半透明遮罩 + 小波浪环），三节与卡片都不动；
- 三节的锚点恒定这条既有红线不受影响（节的数量与次序仍不随数据变）。

⚠️ 这一改要小心"静默交错"：不清 `posts` 就意味着**旧一批与新第一批之间有一个共存窗口**。
所以压指示那一层是必须的（用户看得见"正在换"），而且 `seenKeys` 仍要清空
（否则新一批会被当成"已经摆过"而整批剔空 —— 那会读成"换了一批结果啥也没变"）。

## §4 第 4 条：关注画师跨站合并

### 4.1 冲突（已当面点明，用户推翻旧判据）

`GalleryFollowedArtistsTest` 里现在钉着一条「跨站同名是两条，不并成一条」。
当时的两个理由：两站同名不保证是同一人；点击一枚要用 `site` 单站交接给搜索。
用户 2026-09-30 明确要合并 ⇒ 第一条按"同名即同人"处理（与「最近搜索」跨站合并一条同口径），
第二条换成"不限站搜"（下面）。

### 4.2 口径

- `FollowedArtistRef` 由 `site: GallerySite` 改成 `sites: Set<GallerySite>`（**有货的那几站**）；
- 合并键 = 名字**忽略大小写**（既有那条"不认大小写但摆原样"的判据保留）；
- `count` = 两站合计；`previewUrl` = 两站里**最近一张 previewUrl 非空**的收藏（既有的"最近"口径不变）；
- 排序仍复用 `GalleryArtistFollows.sorted(dedupe(follows))`，只是同一人不再出现两行；
- 徽标：`sites` 里有哪站摆哪枚，两枚并排（拍板）；
- 点击：按这个名字**跨两站搜**。落点是 `GallerySearchViewModel` 新增一枚
  `acceptHandoffAllSites(tags)`（强制 `GallerySearchSource.ALL`），
  既有 `acceptHandoff(site, tags)` 不动 —— 它是别处（大图页标签、搜索卡）在用的口径。
  ⚠️ 不碰保护域（`Navigation.kt` / `VeneraNavTab` / 路由映射 / 齿轮入口）。

## §5 第 5 条：无标题回退

### 5.1 冲突（已当面点明，用户推翻旧判据）

`GalleryCardTitle` 判据 4 原文：「一个都没有 → null，卡片就不摆标题行。
**不拿通用标签或画师名顶包**」，理由是会摆出「掀起上衣」这种不成句的东西、
以及 yande.re 词典名称覆盖约 73% 会时有时无。

还要提醒一句事实：**角色档本来就在标题里**（现口径是「作品 · 角色」），
所以真正走到"没标题"的那批是**既无作品档也无角色档**的图 —— 用户说的"显示角色和其他 tag"
里，"角色"那一半其实已经生效，能新增的只有画师名与通用标签。

### 5.2 口径（拍板：画师名 → 通用标签译名）

回退链变成四档，前一档有就停：

1. 作品 · 角色（既有）
2. 只有作品 / 只有角色（既有）
3. **画师名**（词典 artist 档）—— 成句、且是"这张是谁画的"，最像标题的替代品
4. **第一枚有中文译名的通用标签** —— 兜底；**没有译名的原词不摆**
   （`long_hair` 这种下划线原词摆上去就是"不成句"那类读数的来源，宁缺）

数据面改动：`GalleryTagDictionary.titleTags()` 现在只放行档位 3/4（:134），
要放宽到含 artist 档与"有译名的通用档"，并把档位一起交出去（判据层按档位分先后）。
分批与"打不开回 null"的既有口径不变。

### 9.1 与拍板文字不一致的一处（如实记）

第 1 条拍板的选项文字是"保留上一批 + **压一层轻指示**"，选项里我当时写的是
"整片压一个半透明遮罩 + 小波浪环"。**实际落地的是节头「换一批」旁一枚 `loaderInline`(28dp)
波浪环 + 芯片禁用**，没有整片遮罩。

理由：仓库里没有可用的遮罩透明度口径 —— `maskScrimAlpha = 0.65f` 的语义是**封面打码**、
`selectedSurfaceAlpha = 0.5f` 是**次级表面**，拿任一个来压推荐区都是把语义不同的 token 挪位；
新造一个数字又违反"观感尺寸用现成口径"。而指示摆在节头正是用户刚点下去的位置，
"这一节正在换"这件事说得比整片遮罩更准，也不挡住已经摆好的那批图。
真机若嫌它太弱，改法是把这一枚环换成推荐区顶部一条 `LinearProgressIndicator` 量级的进度条，
而不是回头去造遮罩 alpha。

### 9.2 落地时定死、方案里没写的三条口径

- **合并只发生在名单上**（M5）：只在 y 站关注过的人，卡上只有一枚徽标，
  张数与卡面也**只算 y 站**的收藏 —— 另一站的同名图不算他的。
  否则会出现"摆一枚你没关注过的站的徽标、点进去搜到别人的图"。
- **合并后那条的排位与显示名取组里最近那次关注**（M5）：这样"我刚关注的人在最前"
  在合并之后仍然成立；显示名沿用"不篡改用户看到的字"那条旧口径（用添加时那份大小写）。
  徽标次序则恒为枚举自然序（yande.re 在前），不跟关注时刻飘 —— 同一个人两次进栏
  徽标换边，读起来像换了个人。
- **元数据档（5）永不进标题回退**（M6）：通用档只在**有中文译名**时进表
  （没译名就只剩 `shirt_lift` 这种原词，比空着还难读）；画师档没译名则摆原词
  （专有名词，音译一个反而没人认得出）。
