三条把"容器 alpha 太低"钉死的反证：

  1. 物理上不可能：α·base 叠在任何不暗于纯黑的东西上，最小也是 0.86 × base = #D3C4BE；实测 #C1B3B2 比它还暗 ⇒ 0.86 那一档之后还有一层黑。（编译产物常量池里确认过 0.86f 确实在包里 —— 用户装的就是新包。）
  2. 与背景无关：s2 的页面底 #A5A1A0（L=0.36）与 s3 的 #EFE4E1（L=0.79）亮度差一倍，卡色只动 ±9 ⇒ 那层黑不来自采样底。
  3. 夹在卡底与子元素之间：同一张卡里胶囊是亮的、胶囊周围的卡底是灰的。

成因（逐层核 miuix basic/Surface.kt:128-146）：库把投影挂在 Modifier.graphicsLayer(shadowElevation, shape, clip = false)，而那一格在调用方 modifier 之内：

.veneraGlassSurface(...)            ← 调用方给的，在**外**
  .graphicsLayer(shadowElevation)   ← 库自己加的，在**内**
    .clip(shape).background(color)

Compose 外层先画 ⇒ 真实层序 ① 模糊 → ② 容器色 → ③ 平台投影 → ④ 子元素。不透明底的 Surface 上 ③ 被 ② 盖住；玻璃档 ② 是透明的，③ 那层黑剪影就透出来了 —— 且它在 ④ 之下，所以不透明的胶囊照常发亮。

n=6 vs n=2 的受控对照（最终定案的那一刀）：全仓 8 处玻璃挂载点里，只有这 2 处传了非零 shadowElevation（GalleryHomeChrome 入口条 / GallerySearchArea 搜索卡）—— 而用户 4 张截图里报灰的恰好就是这两个元素。另外 6 处（VeneraCard / VeneraChip / VeneraFilterPill / VeneraControls / SettingsComponents / GallerySheetBlock）没挂投影，截图里全部正常。miuix Card 自身不含 graphicsLayer（已逐字核过），卡片不踩这一脚。

处置：新增 唯一出处 veneraGlassSurface 的姊妹件 veneraSurfaceShadowElevation(solidElevation) —— 玻璃档返 0.dp、实色档照旧。两个调用点改走它。不立新数字：玻璃档的纵深交给模糊与描边高光、实色档交给投影，各归各的。第三轮那个 PanelAlphaLight 保留、但注释与尺子里的归因订正。

结果：用户 12:51 截图确认灰块消失 —— 卡内回到 #F5DDDD(L=0.763)，与页面同一族色。但同一次截图暴露了第三轮 fadeBottomEdge 自己的 bug，见第五轮。

第六轮（2026-10-16 13:1x，结论：能做，未落地）第七轮订正：下面第 3 条与"入口条那一侧"的 API 选型作废，做法已换 · 用户：「另外我想你另外看看画廊的主页搜索框真的做不了容器变化动画吗，现在还是淡出淡入的」

第 3、4 条合起来说明一件事："源那一侧不能撤、得继续占位"这个约束，官方专门开了一颗 API 来满足 —— 而这条约束正是 10-15 那条口径的由来（入口条一撤，墙就上跳一行的距离）。换句话说，当初挡路的那个理由，官方已经有正解了。
订正（第七轮）：那条"源要继续占位"的约束官方确实认，但它给的机制是 sharedBounds 的 placeholderSize（转场期间退出方按内容大小占位），不是那颗 caller-managed 版 —— 那颗在 Android 侧根本调不到。本仓最后的做法更直接：给入口条外面套一层固定高度的框（高度取它自己的自然高度 galleryHomeChromeHeight()），于是转场结束后也照样占着。比 placeholderSize 省事，且不存在"转场一结束墙又跳一下"的尾巴。

那为什么现在还是淡出淡入：现在的实现是 AnimatedVisibility(fadeIn + scaleIn(initialScale = 0.94f, transformOrigin = 顶边中点))。scaleIn 是等比缩放，而"56dp 的入口条 → 约 200dp 的卡"要的是竖向独立插值（宽度其实已经逐像素相同了，第三轮那条满宽改动做的就是这件事）。0.94 对 "56 ÷ 200 = 0.28" 这个落差没有任何表达力 ⇒ 上屏读起来就是"淡入 + 轻微放大"，也就是用户说的"还是淡出淡入的"。不是做不到，是当初拿了一个近似物。

真做的话，三处改动：

  1. 入口条那一侧：sharedBoundsWithCallerManagedVisibility(rememberSharedContentState(key), visible = !svm.active)。选这颗 API 的唯一理由就是 visible = false 时它照旧占着那一行的高度（墙不跳），行内内容淡出。
    订正（第七轮）：那颗 API 调不到（见上）。改成给入口条**也包一层 AnimatedVisibility(visible = !searchOpen)**、挂同一 key 的 sharedBounds；"占位"另用一层固定高度的 Box 兜。额外一条：这一层的 enter/exit 必须用位移恒 0 的 slide而不是 fade（与 renderInOverlayDuringTransition = false 成对，理由见第七轮）。
  2. 卡那一侧：同一把 key、visible = svm.active、resizeMode = RemeasureToBounds。必须 Re-measure 而不是 scaleToBounds：卡里有一枚带文字的输入框，等比拉伸会把那些字拉变形。
  3. 曲线沿用现有的两颗 spring：SEARCH_CARD_SHOW_SPEC / SEARCH_CARD_HIDE_SPEC（= miuix 顶栏居中标题那一对）。这两颗与"居中标题出现"同源是同一条契约，换掉就等于把 10-15 那条又拆了。

三个已知的坎（都要真机才判得出来）：

  1. ⚠️ 玻璃背板（最大的一条）：卡挂 veneraGlassSurface(PANEL)，它的模糊是 textureEffect 去采一块录制下来的背板。共享元素默认 renderInOverlay = true —— 会被搬进 SharedTransitionLayout 的 overlay 里画，那一层在正常绘制序之外，采到的背板可能是空/错位的。首选处置是显式 renderInOverlay = false 让它在原位插值。这一条只能真机看（本轮到"编译 + 单测 + 出包"为止）。
  2. 焦点时序：输入框现在"等一小段再要焦点"，等的就是 AnimatedVisibility 内容 attach 完成。内容组合时机一换，这一档要重调 —— 否则键盘会在飞行途中弹出来。
  3. 收起那一路是第二对：滚到 1/3 时卡收进顶栏那一行胶囊，那是另一半动作。第一轮只做"入口条 ↔ 搜索卡"这一对，收起那一路先不动 —— 一次只动一对，坏了才分得清是哪一对。

建议的落地顺序：一对、renderInOverlay = false、曲线沿用现有两颗 spring。退路是"不做共享元素、改做高度插值"（AnimatedContent + SizeTransform）—— 但那条要么把墙顶下去、要么得把入口条搬进浮层槽位，代价比这条大。等用户发话再动。

resizeModeRemeasureToBounds默认的 scaleToBounds 会把卡里那行输入字与分段器整体缩放。这一下宽度其实几乎不变（两端同吃 screenHorizontal 内缩 ⇒ 第三轮那条满宽改动做的正是这件事），动的只有高度；56 → 200dp 这个量级的等比缩放下文字必糊

本文上半部分（一～三节）保留当时的评审读数与方案 A 全貌；方案 A 里只有"材质"那一条落地，宽度内容驱动 / 描边 / 排行图标三条未采纳（方案 B 取代了"减少遮挡"这个思路）。

一句话结论：这一条不是"好不好看"的问题，是三条硬伤叠在同一块面上。

① 它按上限长、不按内容长 —— 卡宽 272dp，内容只有 162dp，右侧 94dp（占卡宽 35%／占屏宽 23%）是纯遮挡，一寸信息都没有；
② 它的底色是"底下那张图"的函数 —— alpha 0.90 让同一条卡内三处采样得到三个不同底色（#352A28 / #3A3230 / #403635），而旁边的入口条是不透明同色，于是"从入口条原地长出来的同一块面"这条契约在收起的那一下断了；
③ 它里面的胶囊与卡底只差 1.34:1（非文字对比度门槛 3:1）—— 选中态 filter chip 不画描边，两枚胶囊分得开靠的是中间那 4dp 间隙，不是胶囊自己。

美化因此不是加装饰，是把这三条各自收口：宽度改成"内容驱动＋上限兜底"、底色走材质轴、右侧那片死区换成读数。不动高度、不立新数字、不改胶囊组件。

二、问题清单（按优先级）

阻塞 P1 · 卡按上限长、不按内容长：右侧 94dp 是纯遮挡

成因（已定位到行）：GallerySearchArea.kt:350-354 给卡设了 widthIn(max = 屏宽 × 66%)，而 :373 内层 Column 写了 fillMaxWidth() —— 在 Compose 里 fillMaxWidth 取的是传入的最大约束，于是卡的宽度恒等于那个上限，与内容多少无关。:437 那行 Row.fillMaxWidth().horizontalScroll() 同理：横滑容器占满 66%，胶囊靠左排，右边空着。

影响：94dp × 48dp ≈ 4500dp² 的宽度压在图上，不换来任何信息；同时它让整条读起来像"没加载完"。

修法：上限保留（兜住条件很多时的溢出），但卡内不再 fillMaxWidth ⇒ 卡宽 = min(内容 + 2×16dp, 上限)。本例内容 162dp ⇒ 卡宽 194dp，遮挡面积 −29%；若同时做 P4（排行加图标，内容 +20dp）则为 214dp / −21%。

⚠️ 这里正好解释上一轮为什么会翻车：上一轮把 collapsedChipWidthFraction（34%，那是顶栏一行的尺子，它要和居中的大标题抢位）当成卡的固定宽度用，而这一行内容本来就有 162dp + 32dp = 194dp = 屏宽 47% ⇒ 越界被截，用户看到"一枚胶囊被切掉半截"。正确的修法不是把上限调大（那是这一版 66% 的来历，等于用更多遮挡去换不截断），而是"内容驱动 + 上限兜底"。

阻塞 P2 · 材质契约断裂：收起的那一下"同一块面"变了色

成因：GallerySearchArea.kt:344-345 结果态取 surfaceContainerHigh.copy(alpha = tagContainerAlpha)。tagContainerAlpha 是封面标签那一档的现成语义（VeneraTokens.kt:63 = 0.90），被借到了"浮动容器"上 —— 两件事对透明度的要求正好相反：标签要"贴在图上看得出是标签"，容器要"承载文字且恒定"。

而它的兄弟件 GalleryHomeChrome.kt:110-113（那条常驻入口条）用的是不透明的 surfaceContainerHigh，同一形状、同一阴影、同一色槽，文档里写着"三条与搜索卡逐字同源，所以展开成那张卡时是同一块面在长高"。现在：展开态（不透明）→ 结果态（0.90），同一块面在收起过程中改了材质。

更硬的一条：它绕过了 SurfaceMaterial 轴。用户把材质选成"实色"（默认档）时，全站实色，唯独这一条仍然是半透明 —— 这正是本项目明令禁止的假开关形态（"用户明令禁止只在单一档位成立的效果"）。

修法：两态都取不透明 surfaceContainerHigh；要"透"就走 Modifier.veneraGlass(VeneraGlassRole.PANEL, cardShape)（受材质轴控制：实色档就是不透明，玻璃档才有模糊 + 染色 + 高光描边）。见 §3.2。

阻塞 P3 · 胶囊分不开：1.34:1 的边界靠 4dp 间隙在撑

成因：VeneraChip.kt:227-229 —— Filter 变体只有未选中时才画 outline 描边；选中态（= 已包含的筛选条件）没有任何描边，只靠 secondaryContainer 实底。这在本来的语境里没问题（MD3 里选中 filter chip 就是靠容器色差），但那需要卡底是稳定的。现在卡底是 0.90 透底的函数，差值在 1.25～1.48:1 之间浮动 ⇒ 亮图上胶囊等于没有边界。

修法（不动 VeneraChip）：把卡做成实色（P2）之后，胶囊与卡底的差值是可测且恒定的，但按本机这套动态取色算下来仍只有约 1.42:1 —— 所以真正要动的是胶囊自己的身份：在摘要条这一排里给条件胶囊补一层 outlineVariant 发丝描边（或换成"描边 + 淡底"的双线索）。项目里已有先例：Tag 变体就是"淡底 + 极弱描边"，理由写的正是"单纯提高 alpha 若与背景仍接近，边框能保证 Tag 与背景分离"。

建议 P4 · 同一排里"筛选"与"设置"同形，"排除"与"默认"同形

摘要条这一排现在混着两类东西，外观完全一样：筛什么（条件胶囊）与怎么排（排行胶囊）。读者要读完字才知道哪枚是哪类。更难解的是第二组撞车：

  • 排除项 -loli 渲染成描边空胶囊（selected = !excluded 为 false）；
  • 排行处于默认档时也渲染成描边空胶囊（GalleryRanking.NEWEST ⇒ selected = false）。

一个外观两种语义。修法：排行胶囊加前置图标（Icons.Outlined.Sort，VeneraChip 已有 leadingIcon 口子）把它从"条件"里摘出来；排除项给删除线或降一档文字色，别只靠描边。

可选 P5 · 右侧空间换成读数 —— 与"省遮挡"是二选一

P1 修好之后右侧会腾出 78dp。它有两种花法，不能同时要：

  • 空着（推荐）：卡宽 194～214dp，遮挡 −21%～−29%。理由见下面那条"它其实是滚动就走的东西"；
  • 换成读数槽：取数中 → 波浪环（CircularWavyProgressIndicator 本文件已在用）；到位 → 128 张（type.caption + textSecondary）。加上它卡宽回到 ≈277dp，省下的遮挡被吃光。

为什么倾向空着：这一条只在滚到顶时存在 —— searchCollapsed（GalleryScreen.kt:638）在顶栏折平那一刻就把整条收走、换成顶栏那一行胶囊。也就是说用户一旦开始看图，这条就没了。一个"滚动即消失"的浮层，首要任务是别挡东西，而不是多装读数。结果规模本来就有两个归宿：页尾 GallerySearchEnd，以及"还想知道"时点开搜索。

建议 P6 · 展开态：已选条件没有行数上限

:416-435 的 FlowRow 是自由的：条件多了它会一直换行，而卡片只有 heightIn(min = …)。listMaxHeight 管的是补全列表（2 / 4 行封顶），管不到胶囊。八枚条件就能把卡顶到半屏，把补全列表和网格一起挤掉。

修法：胶囊行限 2 行，溢出收成一枚 +N 尾枚（点它展开成完整条件页/继续换行）。

可选 P7 · 吸附态（顶栏那一行）才是"看图时的常驻读数位"

GallerySearchCollapsedChips（:1230）刻意只摆条件胶囊、不摆排行，理由是那一行宽度封在 34%、要和居中大标题抢位。后果是：用户往下滑看图时，"这一墙是 2008 年的"这条信息正好消失 —— 而那正是最需要它的时刻（"为什么全是三年前的图"）。

同一处还欠另一件事：缺席原因（GalleryNotices）目前只住在展开区（GallerySearchArea.kt:742 / 757 / 766 / 777），收成一条时整块不画。而结果态那条摘要条滚动即消失（见 P5），所以"这一轮哪条腿没跑起来"在真正看图的那一段时间里，屏上没有任何落点 —— 这是本仓自己记在注释里的已知痛点。

修法（一条改动，两件事一起解决，且不破 34% 封顶）：吸附态不再逐枚摆胶囊，改成一行摘要：

  • 「loli · 排行 年2008」，超出用 +N 收尾 —— 排行档因此常驻；
  • 有腿缺席时前置一枚小警示字形（tertiaryContainer 系），点它回展开态。

顺带让两种收起形态的信息口径统一：现在一个是"全部胶囊"、一个是"缺了排行的胶囊"，同一次搜索在两种形态下说两套话。

可选 P8 · 顶栏三枚圆钮同权重，其中两枚都在"改搜索"

结果态下顶栏是 🔍（改条件）＋ ✕（关搜索，只隐藏不清条件）＋ 🕘（历史）三枚同径 40dp 圆钮并排（实测：直径 103px ÷ 2.625 = 39.2dp ≈ iconButtonSize，圆心间距 48dp = 40 + space4），而摘要条本体也是"点哪都能改条件"的入口。✕ 在搜索语境里常被读成"清空条件"（实际语义是"收起搜索 UI、退回猜你喜欢"，closeSearch() 只把 active = false）。

修法（择一，不必都做）：结果态下撤掉顶栏那枚 🔍（摘要条自己已是最显眼的入口，且修好 P5 后它带读数、更像控件）；或给 ✕ 单独一档视觉（例如放进实底容器），让它不可能被误读成"清空"。

3.2 底色：走材质轴（修 P2 / P3 的一半）

默认档（SurfaceMaterial = SOLID）

两态都取不透明 tokens.color.surfaceContainerHigh —— 与入口条同源，收起/展开是同一块面在变大小，契约接回来。底色从此是常量。

玻璃档（= LIQUID_GLASS）

卡底透明 + Modifier.veneraGlass(VeneraGlassRole.PANEL, cardShape) —— 拿到模糊 + GlassTintAlpha 染色 + 玻璃描边高光。这一档是真的"透"（容器 alpha 0.28），不是 0.90 的伪透。

PANEL 与 CARD 同属 CONTAINER 档，走的是同一套读数（SurfaceMaterialPolicy），没有新数字。

这一条同时兑现了项目自己的规矩：任何"看起来更透"的效果必须在两个档位下都成立，否则就是假开关。0.90 那版在实色档下偷偷半透明，是最典型的形态。

3.3 胶囊身份（修 P3 / P4）

  • 条件胶囊（结果态这一排）：补一层 outlineVariant 发丝描边。理由与 Tag 变体同源 —— 底色差不够时用描边保证分离。只在摘要条这一排加，展开态那一排不加（那里卡底是不透明的，差值本来就够，而且 FlowRow 更要紧的是密度）。
  • 排行胶囊：leadingIcon = Icons.Outlined.Sort，与条件胶囊一眼分形。
  • 排除项：在 -loli 的描边之外加删除线（或文字退到 textSecondary），不要和"默认排行"共用一个外观。

4.2 材质（方案 A 里唯一落地的那一条）

原先 surfaceContainerHigh.copy(alpha = tagContainerAlpha) 是伪透，两处都错：

  • 绕过材质轴 —— 用户把 SurfaceMaterial 切到"实色"，这一张照旧半透明，正是本仓明令禁止的假开关（与 veneraGlassCardColors 头注同一条）；
  • 0.90 落在最不划算的凹谷 —— 只透 10%，读不出玻璃，却足够把卡色染成底下那张图的颜色（真机采样：同卡内三点 #352A28 / #3A3230 / #403635 各不相同）。

现在两态同一个材质：实色档不透明铺 surfaceContainerHigh；玻璃档底色置透明、由 veneraGlassSurface(PANEL, extraLarge) 采氛围层做真模糊。入口条（GalleryHomeChrome）同步改 —— 否则"从入口条原地长出来的同一块面"这条契约会在按下那一下又断一次（从前的断法是实色 vs 0.90 伪透，现在是玻璃档下一条玻璃一条实色）。

玻璃采的是氛围层（全站唯一采样源，静态 Canvas），不采页面内容 —— 所以卡压在图上也不会"模糊了底下那张图"，且滚动时不重捕。

四·三、滚动收起：时机对齐居中标题，曲线与它同源 已落地

用户口径（原话）：「当向上滑动内容到显示居中标题的时候搜索栏收入消失，向下拉到最顶的位置才重新显示，必须要有弹性过渡，且过渡动画自然」。

两条都落在 1/3 ⇒ 取同一个值，于是"居中标题一出来"与"搜索卡收起"是同一件事的两面，而不是先后两下。从前这里是 COLLAPSE_SETTLED_FRACTION = 0.99（完全折平才收）—— 用户真机读到的是"我都滚过一屏了它还在"。

4.3.2 回程：为什么要滞回

单阈值做不到口径的后半截 —— 那样滚回 1/3 之上它就会弹回来，而"退回到刚刚折平的位置"与"回顶"在用户心里是两件事。所以两个方向各给一条：上滑越过 1/3 ⇒ 收起；下滑回到 ≤ 0.02 ⇒ 才放出来（几乎到顶）。

图 4 · 收起 / 恢复的两个阈值与三件东西的状态。中间那一段（0.02 < frac < 1/3）是滞回区：两边都不动，不会来回跳。

4.3.3 曲线：抄顶栏居中标题那一颗 spring，不另立一条

收起/展开出场取 folmeSpring(damping = 1.0f, response = 0.3f)（显示）与 0.15f（隐藏）—— 与 TopAppBar.kt:688 那两颗逐字同源。抄同一颗曲线是刻意的：居中标题淡入与搜索卡收起在同一帧触发，若两边曲线不同，用户读到的是"两个东西各动各的"；同源之后它是一个动作。

  • 方向仍锚在顶边中点（transformOrigin = TransformOrigin(0.5f, 0f)）—— 收回去读起来是"这条入口条自己缩回顶栏"，不是"一块面板淡出"；
  • damping = 1.0 是临界阻尼、不过冲：alpha 与 scale 都不会越界闪一下。弹性来自曲线形状（速度先快后缓、带 settle 尾巴），不是靠回弹；
  • 吸附胶囊那一行的 slideInVertically 用同一组参数的另一份实例（它的 spec 类型是 FiniteAnimationSpec<IntOffset>，与 Float 不是同一个类型参数，必须按类型各建一份，参数值相同）。

判据走 snapshotFlow { collapsedFraction } 而不是 derivedStateOf：滞回有记忆、要写状态，而 derivedStateOf 只能算纯函数。滚动全程只在越线那两下各写一次，不是逐帧写。

  • 本轮 回程滞回：下滑到 frac ≈ 1/3 以内时不恢复；只有拉回接近顶部（≤ 0.02）才重新显示。
  • 本轮 过渡自然：收起/展开是弹性曲线（folmeSpring，与居中标题同源）—— 不出现"卡片瞬间消失"或"两个东西各动各的"；不要用 220ms 线性 tween 的观感去验收。

  • 第四轮采纳 玻璃面无投影：浅色下不许再出现"色块"。判据是层序而不是颜色值 —— 玻璃档 shadowElevation 必须为 0，因而卡底不得比它自己那块 surfaceContainerHigh 暗出可测量的一档。反过来说：不要用"容器 alpha 调了多少"去验收这一条（第三轮就是栽在这个误判上，把 0.22 抬到 0.86 之后灰块一点没退）。
  • 第五轮采纳 被切断的内容用渐隐收口，且渐隐必须关在离屏层里：判据是"渐变终点是不是卡自己的色"，而不是"有没有渐变"。终点是纯黑（#0F0B08 那一档）就说明 DstIn 穿透到了窗口层 —— 那种形状与"露出卡底之下那张图"不同：后者会看到图的内容，不会有单调梯度，也不会横向正好止于卡内宽度。
  • 第七轮采纳 入口条 ↔ 搜索卡是真容器变化，不是淡入：判据是"卡的初始高度是不是等于入口条的高度"，而不是"有没有动画"（第七轮之前那颗 scaleIn(0.94) 的初始高度是 卡高 × 0.94 ≈188dp，与入口条的 56dp 差着一整个数量级 —— 所以它必然读成淡入）。不要用"动画时长 / 曲线调了没有"去验收这一条（第三轮就是拿 alpha 去顶一个层序问题的同类误判）。做法与三条取舍见开头第七轮，那儿同时记着真机上待判的两处（玻璃档模糊 / 焦点时序）。
  • 未采纳 高度纪律：展开态 8 枚条件时胶囊行仍会无上限换行（原 P6，待定）。
