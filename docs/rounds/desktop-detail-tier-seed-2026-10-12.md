## 1 「写进初值」那一版是错的，且错在屏上量不出来

第一眼的设计（也是这一批本来会写的形状）：

```kotlin
var tier by remember { mutableStateOf(startDetailTier ?: desktopDetailInitialTier(previewQuality)) }
```

它**永远不会生效**。点卡那一路（`VeneraDesktopApp.kt` 里那枚共用的 `LocalDesktopWallPick`）紧跟着执行

```kotlin
desktopViewerEntryTier(desktopDetailTiers(picked.post, picked.masked))?.let { entry -> tier = entry }
```

= 把档位升到「大图」。而取证那颗 `--detail` **走的正是同一枚 lambda**（五面墙不用改签名就能自开浮层，第五十一批那一格）。于是 stdout 念过「认成 档=原图」而屏上是「大图」档 —— 本仓量过四次的「stdout 念了而屏上没动」那一族的**第五次**，差别只在这一次是**读代码读出来的**，没有起窗、没有图证。

为什么当时能读出来：批 92 的前一步是找"档位落在哪一格"，把 `tier` 的所有写点列了一遍（`onTierChange`、点卡升档、初值）——列出来才发现第二枚写点排在第一枚**之后的同一帧里**。**这一条值得记进方法**：加种子之前先把目标状态的所有写点数一遍，写点比参数多时，落点必须选在最后一个写点那里。

所以落点在点卡那一跳，且初值那一格保持原样（`desktopDetailInitialTier(previewQuality)` 仍是"没给种子时"的来源）。

## 2 顺带量到的两条轨（这是本批的产品缺陷，不是取证缺口）

`desktopDetailTiers` 那张表会说"这一张该摆哪几档"（被挡住 ⇒ 一档不摆；视频与站方没给 `file_url` ⇒ 撤「原图」）。浮层读了它并会钳：手里那档摆不出就落回这一张的第一档。**大图那一屏与预取没有钳**：

- `DesktopGalleryViewer.kt` 取址 `desktopDetailTierUrl(it.post, tier)` —— 吃的是根上那颗**原始状态**；
- `VeneraDesktopApp.kt` 预取那一跳 `desktopPreloadPlan(preloadMode, …, tier)` —— 同一枚。

真实路径（用户今天就能踩，不需要任何参数）：点卡 → 档排选「原图」→ 按「下一张」翻到一条视频。此时
- 浮层那张图：走钳档 ⇒ 显示静帧（对）；
- 大图那一屏：取 `post.fileUrl` = 原片 mp4 ⇒ 解码失败那一句压在静帧上面；
- 预取：把原片 mp4 排进 Coil 的队列（白花一趟流量，而那一张永远不会上屏）。

改法：钳档算式收成一颗 `desktopDetailTierForCard(tier, tiers)`，根上算一次 `effectiveTier` 递给三条轨；浮层那一行改吃同一颗函数（不再是内联那份），那一层不改（它只吃自己那枚形参，取址处仍全文件一处 —— `DesktopGalleryViewerTest` ① 那把尺子一字未动）。

⚠️ 这条缺陷**不是靠这一批的判据发现的**，是靠"要给档位加种子"时把写点与读点列出来发现的。**记法**：给一个已有状态加第四个入口（参数）之前，先审它现有的入口与出口是否同轨 —— 新入口永远是最容易暴露不同轨的那一刻。

### 5.1 P9 那一笔没咬住 —— 本批最值钱的一条

原判据 ⑥ 里那一枚写的是：

```kotlin
assertTrue("大图那一屏还在吃未钳的那枚：" + app, app.contains("tier = effectiveTier,"))
```

P9 把**大图那一层**的实参改回 `tier = tier,`（正是这一批修掉的那条缺陷的形状），判据**照样绿**。理由不是代码写错了，是**锚点被同屏另一处合法调用喂饱**：应用根里 `tier = effectiveTier,` 有**两处**（那一层 + 浮层面板），撤掉一处还剩一处，`contains` 看不出差别。

这正是本仓已经记过的那一条 —— **「"某一处调用必须存在"的锚点会被同屏另一处合法调用喂饱（接线类要数出现次数）」**，而这次是**自己新立的尺子当场栽进去**，且栽的是这一批唯一那条"缺陷已修"的判据（⑥ 若不算数，这一批的产品修复就没有尺子管着）。

改法（同批落地，改完单跑 P9 复验）：

```kotlin
assertEquals("应用根里 `tier = effectiveTier,` 应恰好两处（那一层 + 面板）：" + app, 2, codeOccurrences(appFile, "tier = effectiveTier,"))
assertEquals("三条轨里还有一条吃未钳的那枚：" + app, 0, codeOccurrences(appFile, "tier = tier,"))
```

一条计数（钉"两处都在"）+ 一条负向（钉"旧那枚一枚不许留"）。**加一条尺子而不是改宽那条尺子** —— 与批 89/90 那两次的处置同一口径。

### 6.1 这一趟把**核对工具**自己钉了一遍

拿 `_qa/b89_check_frame_alignment.js` 复算 pkgOrig 那一行时，第一次报的是对不上：复算 `内容=0,497,…` 而屏上念 `0,498,…`。
定位：工具把显示尺寸**先取整**（`dh = round(423×2.5) = 1058`）再拿去算位置，而产品那颗 `DesktopVisibleRegion.contentRect` 是**位置吃浮点**（`410.5 − 1057.5/2 + 615.75 = 497.5 → 498`）、只有宽高分开取整。前四趟的 `fitH × 倍` 都正好是整数 ⇒ 工具顶上那句"与 Kotlin 那四处算式逐字同形"**从没被量过**。
处置两条：**改工具**（不动产品 —— 产品的写法才是那 30 条判据钉住的那一枚），并**把这条约定钉成判据**：`DesktopRegionDecodeTest.半像素那一档位置吃浮点而宽高各自取整`，期望值逐字取自包内那一行，带整数那一档的对照组；台架 **P19** 打的正是它（改完后它一处红、其余 30 条不跟着红）。
⚠️ 顺带记一句形状：`top` 与 `height` 各自取整时 `top + height` 与浮点真值可以差 1 px —— 这落在摆位不变量的 ±2 容差里，**屏上看不出来**，所以这一格能钉的只有"约定不许换"，而不是"结果更准"。
