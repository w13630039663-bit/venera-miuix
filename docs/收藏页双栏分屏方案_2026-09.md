# 收藏页双栏/三栏分屏（Split-pane）方案

日期：2026-09-22　状态：待拍板，未动代码

## 0. 调研结论（能力边界，已核实）

**官方库现成可用，不用造轮子：**
- `androidx.compose.material3:material3-adaptive` 最新 **1.0.0-alpha06**（Maven metadata 实查，无 1.4/1.5 系）。
  其 `.module` 依赖声明实查：foundation 1.6.0-rc01、window-size-class 1.2.0-rc01，**不钉 material3 主模块版本**
  → 不会把本项目被 Miuix 顶死的 `material3 1.5.0-alpha22` 挪位，版本约束安全。
- 提供 MD3 Adaptive 官方组件：`ListDetailPaneScaffold`（列表-详情双栏）、
  `rememberListDetailPaneScaffoldNavigator`（含断点判定 + 锚点导航）、
  `AdaptiveInfo`/`WindowSizeClass`（MD3 标准断点：<600dp compact / 600–839 medium / ≥840 expanded）。
- `material3-window-size-class` 已在本地 gradle 缓存（1.4.0 / 1.5.0-alpha22），编译无网障。
- minSdk 33 / compileSdk 37，全部满足。

**这就是 MD3 标准答案**：Google 官方文档里 iPad 邮件/设置那种「列表常驻 + 详情滑出」
的范式就是 Material Adaptive 的 List-Detail 布局，库内建断点切换与转场，符合「符合 md3 标准」的要求。

**参考项目佐证**（不抄实现，只证模式）：
- 本仓库 master（Flutter 原版）：收藏页宽屏本来就是「侧栏 + 内容」双栏（`side_bar.dart`），
  窄屏退化为抽屉——本方案等于把原版断档的能力在 Compose 侧恢复，不是新发明。
- `build/pixez`（同栈参考项目）的 HistoryScreen 为单栏，无现成分栏实现可抄，故以官方库为准。

## 1. 目标行为

| 档位 | 宽度 | 布局 | 点卡片的行为 |
|---|---|---|---|
| 手机/竖屏 | <600dp (compact) | 单栏（现状） | 跳转详情页新页面，**与现在逐字节一致，零回归** |
| 小平板/折叠 | 600–839dp (medium) | 双栏：左=收藏列表，右=详情 | 右栏原地滑出详情，列表不动 |
| 大平板/横屏 | ≥840dp (expanded) | 三栏：左=收藏夹导航栏，中=列表，右=详情 | 同上；左栏切换收藏夹 |

- 右栏详情内点「继续阅读」→ 阅读器**全宽覆盖整个窗口**（推入壳 NavHost 的 ReaderRoute），
  读完返回落回分栏、列表与选中项都还在。阅读器不塞进右栏（见 3.4 裁决）。
- 「滑出」动效：详情栏从右侧滑入（MD3 标准 content-enter 配方：emphasized 空间 + enter 250ms / exit 200ms 量级），
  手机端列表→详情的 shared axis X 转场在平板分栏内不再触发（分栏没有「下一页」）。

## 2. 架构方案（推荐 A，备选 B）

### 方案 A（推荐）：分栏收在收藏页内部，导航栈零改动

```
壳 NavHost（MainActivity，现状不动）
 └─ composable<FavoritesRoute>
     └─ AndroidFavoritesScreen
         ├─ compact → 现结构：FavoriteGrid / NetworkFavorites 全屏
         └─ medium+ → ListDetailPaneScaffold(DetailPane=选中漫画)
             ├─ ListPane  = 现有 FavoriteGrid（窄化宽度，chips→左栏或保留）
             └─ DetailPane = 内嵌小 NavHost，push DetailRoute
```

要点：
- **DetailPane 里放一个内嵌 NavHost** 复用现有 `composable<DetailRoute>` 那一支的接线
  （`viewModel()` 随 nav 条目作用域、`CoverTransitionHost` 的共享元素 provide、`resolveDetailComic`
  全部原样生效）——详情栏不再是「重建组合的普通子组合」，规避已知的
  「导航条目重建打回默认值」一族坑（[[project-nav-entry-recomposition]]、[[project-navigation-predictive-back-facts]]）。
- 列表→详情的**封面共享元素飞行在同一个 SharedTransitionLayout 内**（同 Activity），
  两端 key 同串约束天然满足（[[project-shared-element-transition]]）。
- 返回语义：medium+ 且 Detail 打开时，系统返回/预测返回第一下**收起详情栏**（恢复列表），
  第二下才走现状。走页内已有的 `rememberPredictiveBackState` 模式
  （多选条已用过同一条路，FavoritesScreen.kt:128）。
- 底栏：分栏属主 Tab，悬浮底栏 overlay 照旧显示；列表与详情栏底部按既有
  `bottomBarClearance` 契约避让，不新增几何 magic number。
- 三栏的左栏 = 把现在网格头部的 `FolderChipRow` 升级为 MD3 `NavigationRail`
  （收藏/历史/下载等一级入口 + 其下收藏夹列表，对齐原版 side_bar 的层级），
  medium 双栏时 chips 保留在列表头部不动。

改动面：`FavoritesScreen.kt`（结构分支）、`Navigation.kt`（openComic 在分栏档改为驱动分栏状态、
详情内嵌图接线）、`build.gradle.kts`/`libs.versions.toml`（+material3-adaptive 一个依赖）。
HistoryScreen 后续可用同一个小结（先收藏页试点，验证后再铺）。

### 方案 B（不推荐，列为对照）：Activity 级双栏

整个壳升为 `SupportingPaneScaffold`，详情成为独立 supporting pane Activity。
官方「跨 Activity 才有系统级预测返回动画」在双栏间**不适用**（同任务内列表→详情不是换页），
收益为零；改动面却覆盖 MainActivity/SettingsActivity/交接槽全链。
且与已拍板的「设置子树走真·跨 Activity」方向正交冲突。**排除。**

## 3. 逐层裁决点（需要你点头的）

3.1 **档位阈值**：取 MD3 官方断点 600/840dp，不自造口径。→ 默认照办。
3.2 **展开档默认选中项**：进页右栏空置占位（「从左侧选择一本漫画」+ 弱色图标），还是默认打开第一条？
    邮件 App 行为 = 不默认打开。**我推荐占位**，避免进页即发一次详情网络请求。
3.3 **medium 档收藏夹入口**：chips 留在列表头部（改动最小）；还是 medium 就并成独立导航列（提前三栏）？
    **我推荐前者**（跟随库的 ListDetail 两栏语义，expanded 才出第三栏）。
3.4 **阅读器进右栏？**：不做。阅读器是沉浸全屏体验，Flutter 原版宽屏也是整窗阅读；
    塞右栏会撞满宽翻页手势和状态栏几何。**全宽覆盖、返回落回分栏。**
3.5 **网络收藏 Tab 同样适用**？本地/网络两个 mode 共用分栏外壳（网络收藏列表本身是单列行卡，天然适配左栏）。→ 默认照办。
3.6 **多选/排序/顶栏折叠**在分栏下如何摆：顶栏只覆盖左栏（列表区），详情栏保留自己的返回箭头与顶栏；
    多选条仍挂在左栏顶。→ 默认照办，真机观感验收。

## 4. 风险与降级（宁可错慢，不可静默交错）

- **库是 alpha06**：API 面 `@ExperimentalMaterial3AdaptiveApi`，`OptIn` 包裹集中在一个新文件，
  将来升版只动一处。若库行为异常（锚点切换不跟断点），降级路径 = 用 window-size-class（已缓存）
  手写 `Row { 列表 weight / AnimatedVisibility 详情 }`——视觉一致，仅少库的窗口测量自动化。
- **零回归线**：compact 分支编译期短路，不进分栏代码路径；手机端现行为逐字节不变。
- **不静默交错**：DetailRoute 载荷解不到（selectedComic 与 route 不同源同 id）时走现有
  `resolveDetailComic` 的空壳兜底 + 详情页自己重拉，这条链现状已有，分栏不新建旁路。
- 平板验证：Pixel Tablet 模拟器（1280×800，840dp+ 进三栏；注意 [[project-venera-qa-device]] 的黑边坑——AVD 第二屏）。
  手机侧由你在真机确认 compact 零变化，我不代操作设备。

## 5. 实施步骤（拍板后）

1. 依赖接入 + 断点探测小工具（`rememberVeneraWindowWidthSizeClass`，包一层 AdaptiveInfo）。
2. `FavoritesScreen` 分栏骨架：ListDetailPaneScaffold + 内嵌详情 NavHost（方案 A）。
3. 返回语义：分栏内「先收详情再退页」接 `rememberPredictiveBackState`。
4. expanded 三栏：收藏夹 NavigationRail（含切分 FolderChipRow 的数据面）。
5. 动效收口：详情滑入/滑出时长曲线对齐 MD3 tokens，与封面飞行不打架。
6. 真机 + 模拟器验收（compact 零回归 / medium 双栏 / expanded 三栏 / 阅读返回落点）。

预计改动 4~6 个文件，核心新增一个 ~200 行的分栏宿主。

## 附二：2026-09-23 手机真机第二轮反馈（用户令：平板档不动，只改手机）

1. **分段控制器「滑块撑满半边、没有药丸中的药丸感」= 真 bug，不是观感问题**。
   `VeneraSegmentedButton` 选中块偏移写成 `gap + i*(cellW+gap)`，但当时 Row **并没有** `spacedBy`，
   单元之间无真实间隙 → 选中块整体右溢一个多 gap，顶穿容器内缩贴上描边，看着就是直角矩形。
   修法：Row 补 `spacedBy(gap)` 让间隙真实存在，偏移改 `i*(cellW+gap)`，分隔线右移半个 gap 落进间隙正中。
   **平板档的 48/56dp 高度与字号档位一律未改。**
2. **右上角布局钮太大/太贴角/图标不好看**：容器由自造 36dp 改用现成 `iconButtonSize`(40dp) 触达档、
   图标收到 `badgeIconSize`(18dp)、补 hairline 描边（原先只有半透明底，深色背景上几乎不可见，
   于是只剩一个粉色大图标粘在角上）。网格档曾试 `GridView`→`SpaceDashboard`（圆角方块），
   **用户否掉，已退回 `GridView`**（与 `ComicTileLayout` 原始共用钮同一对 glyph）。
   该钮此时已被并发改动收进顶栏 `actions`，贴边由栏内标准内边距解决。
3. **「全部」pill 孤立**：文件夹 ≤1 个时整行不渲染（单个「全部」不提供任何选择）。
   网络侧与本地侧（网格头 `fav-folders` item）同一处置。
4. **网络收藏排第一**：段序 `favoritesModesNetworkFirst = [Network, Local]`；默认值本就是 Network。

**胶囊收口**：`FilterPill` 由 `NetworkFavoritesScreen` 私有提升为公共 `components/venera/VeneraFilterPill.kt`，

  改为按 `comic_id` 从两处本地真相反查（`FavoriteImagesManager.authorIndex`）：
  ① 本地收藏的 `author` 字段，空则回落作者类标签；② `reading_stats.tags`。
  查不到就留空行位，**不拿源名顶上**。

  这正是用户报「画师统计不到」的根因；`ReadingStatsManager.TAG_SEPARATOR`（`U+001F`）

## 附八：2026-09-23 手机分段器选中块偏左 —— 是 px 当 dp 用，不是居中没做好

用户截图「还是有点向左了」。先用像素级测量把话说死（PowerShell + System.Drawing 逐行扫描边）：
容器 x 134..944、中心 539，屏宽 1079、中心 539.5 —— **容器本身是正居中的**；三段标签中心
279 / 540 / 804 也与三格中心 272.5 / 539 / 805.5 对齐 —— **Row 排布也是对的**。
只有实心选中块落在 404..635（中心 519.5），比它该在的 421.8..656 左移 ~17px。

- **根因**：`gapPx` 是像素（`segmentedGap.toPx()`），却被直接当 dp 用进布局 ——
  `padding(gapPx.dp)` 与 `spacedBy(gapPx.dp)` 让位的是「4×密度」dp，而选中块的位移算式
  `i*(cellW+gapPx)` 用的是「4dp」像素。两者差着一倍密度，块就落在格子偏左处。
  **第 0 段偏移恒为 0 所以永远看着是对的**，段数越多偏得越远（index 2 已偏出 ~34px），
  这就是上一轮把宽度改成「按段数推导」之后仍然偏左的原因。分隔线的 `gapPx/2` 居中量同样偏。
- **修法**：布局侧一律用 Dp（`padding(gap)` / `spacedBy(gap)`），像素值只留给 offset。
- **顺带把 token 从 4dp 提到 space5(10dp)**：真机上原本渲染出的环宽就是 4×密度 ≈ 10.5dp，
  用户已拍板的正是这个观感；单位改对后若仍留 4dp，环会从 10.5dp 掉到 4dp、药丸明显变粗贴边。
  取现成的 space5 而不是造 10.5 这个数，观感与改前差 1.3px（块高 70→73.5px），
  且不再随密度漂移（平板密度 2.0 时原本是 8dp，现在两档都是 10dp）。

## 附十：2026-09-23 修「预览页返回两次后整屏 UI 消失」—— 槽位式载荷不能用在非叶子目的地

真机报的：图片收藏 → 预览页 → 点大图进阅读器（经详情页）→ 返回详情 → 返回 → **整屏 UI 消失**，
再按一次返回才回到图片收藏。

- **根因**：预览页的载荷走的是 `shell.pendingFavoriteImage` +「取用一次即清 + `onDispose` 兜底」，
  这套纪律是从 `ReaderRoute`/`pendingSession` 抄来的。但那条纪律**只对叶子目的地成立**：
  预览页下面还能压详情页，从详情页返回时这条目的地**重新进组合**，`remember {}` 重跑，
  而槽位已在它自己退场时被 `onDispose` 清空 → 读到 null → 走进「取不到就 pop」分支，
  于是既渲染不出内容（整屏空），又自行弹掉一次。
  「再按一次才有收藏页」也对得上：那次自 pop 发生在返回动画进行中，`popBackStack()` 被吞，
  空壳就一直挂着。
- **第一版修法把崩溃引入了**：`FavoriteImageItem` 标 `@Serializable` 整条塞进导航参数
  （`FavoriteImageRoute(item)`）。真机结果是**冷启动即闪**，栈在
  `RouteSerializerKt.generateRoutePattern`：`could not find any NavType for argument item
  of type FavoriteImageItem - typeMap received was {}` —— type-safe 导航对自定义对象
  需要 safeargs 插件生成 NavType，本仓库没装，`typeMap` 是空的。这条已回退。
- **最终修法**：路由只带 `itemId: Long`（内建类型），载荷放 `VeneraShellViewModel.favoriteImagePayloads`
  这张 `id → item` 的表里，**且不在 `onDispose` 清、目的地每次重组都回读**。
  这样两条都堵住：既没有 safeargs 那个崩溃，也没有"取用一次即清"在非叶子目的地上的时机竞态。
  表随 Activity 一起没，量级每条几百字节；只有进程被杀后恢复才会回读不到，那时如实 pop。
  设置页那条 `SettingsEscape.PreviewPage` 同步改。
- **留给后面的判据（两条）**：① 往某条目的地放载荷前先问「它下面还会不会被压页」——
  会，就不能用一次性槽位。② 导航参数只能用内建类型；要传对象，先确认 safeargs 装没装，
  别拿 `@Serializable` 当通行证（它只保证能序列化，不保证导航层能解析）。

## 附十一：2026-09-23 「历史页整屏空白封面」的两条独立成因 —— 熔断被图片打开口 / 会话封面照抄入口空值

用户报：从图片收藏点开大图进播放页之后，历史记录的封面不显示了；「除此之外也经常显示不出来图片」。

- **先说定性过程，因为它推翻了我的第一判断**。我按熔断假说改完装上后，实测那张空白卡
  **一条 Coil 失败日志都没有** —— 而这次新装的 `VeneraImageLogger` 是会打的，所以"没有日志"
  本身就是证据：请求压根没发出。于是 `adb exec-out run-as <pkg> cat databases/venera_core.db`
  把库拉下来用 `node:sqlite` 读（注意 node 在 Windows 下看不到 `/tmp`，要给 `C:/...` 路径），
  `comic_history` 里这条 `cover_url` 是**空串**，16 条历史只有它空。再看 `favorite_images`：
  同一本 `comic_id`、`page_index=13`，与历史那条 `last_page_index=13` 严丝合缝 ——
  它正是「插图收藏 → 读到该页」写出来的。所以空白卡与熔断无关，是两条独立成因，都要修。
- **成因 A：封面空串被写进历史表**。链条是
  `FavoriteImageItem.toComicItem()` 有意留空封面（真封面本就该由详情页拉，见其 KDoc）
  → `shell.selectedComic` → `openChapter(comic = 那个入口条目)` 把**入口**的 `coverUrl`
  原样塞进 `ReaderSession` → 阅读器 `saveHistory(coverUrl = session.coverUrl)` → 库里落空串
  → 历史卡成为一个连请求都不发的空白框。
  修法：`openChapter` 开头先算 `sessionCover`（`details.comic.cover` 优先、空则退回入口值 ——
  与 `ComicDetailScreen` 头部封面同一口径），三处消费它：两条 `ReaderSession`（本地已下载 /
  在线解析）、以及 `publishForUrls` 的封面头。最后这处原本写 `if (comic.coverUrl.isNotEmpty())`
  才发布，入口封面为空时**整步跳过**，picacg 这类封面必须带防盗头的站就 403 ——
  这是「经常显示不出来」的另一块料。
- **第二道闸在 DAO**：`HistoryDao.saveHistory` 用 `CONFLICT_REPLACE`，语义是**删整行再插**，
  不是逐列更新。入口数据不全时它会把这行已有的好封面一起抹掉，且之后不会再写 → 永不自愈。
  改成新值为空时沿用旧值。
  注：已经写空的那条历史记录不会自己长回来，重新点开那本读一次（或删掉该条）才补得上。
- **成因 B：图片把域名熔断器打开口**（这条与 A 无关，是"整屏"级的那种失败）。全站只有一个
  OkHttpClient，`HostCircuitBreakerInterceptor` 挂在链最外层，同一 host 连续 2 笔超时就把
  **整个域名拉黑 60s**。而图片 CDN 偶发超时是常态，预览页那张又是原图（大、慢、最容易撞读超时），
  一撞就把该源图床黑掉 → 同页所有封面一起快败；60s 后半开，再撞两笔又黑 —— 观感就是"经常不显示"。
  反向也被污染：图片请求成功会 `recordSuccess` 把真死域名的失败计数清零，等于让聚合搜索里
  那些死域名重新慢起来。所以图片既不该快败、也不该计数。
  修法：`ImageFetchTag` 标记 + 熔断器见到即 `chain.proceed`。三路打 tag：
  `VeneraImageFetcher`（在线取图）、`ImagePipelinePolicy.fetchSpriteSheet`（EH 雪碧图）、
  `DownloadManager.downloadSingleImage`（下载落盘 —— 它失败该由下载任务自己重试，不该顺手黑站）。
- **给后面的判据**：`AsyncImage` 没配 error 占位，"加载失败"和"压根没发请求"在界面上是**同一个
  空白框**，而 Coil 不装 Logger 时失败完全静默。这类问题先给静默面装日志出口，再谈定位 ——
  否则只能靠猜，我这次就先猜错了一次。
