并存规则：WinUI3 出骨架，幻想乡出皮肤

1两级导航：rail 48 = 域（图库/漫画/设置），pane 224 = 域内页。Fluent NavigationView 有对应模式，选中态仍是 3px 指示条 + Layer 底色。 2中性 surface 阶梯一分未动（#202020 / #272727 / #2C2C2C / #353535），和色只进强调位：博丽朱用于当前筛选 chip 与鸟居，藤紫用于选中态。 3非对称来自"hero 占 1fr + 右侧两小卡固定 320"，以及网格首格跨 2 列 16:10；列数公式仍是每列 200，净宽 1168 → 6 列。但桌面默认窗是 1080×760（VeneraDesktop.kt）⇒ 扣掉 rail 48 与 pane 224 之后净宽 808、再扣横向内边距 24 = 784 ⇒ 4 列，由 DesktopGalleryMetrics.imageWallColumnCount 与 DesktopWidthCaliberDriftTest 钉死。稿上 1440 那档的 6 列只在更宽的窗上成立。 4东方语汇全部自绘矢量：鸟居（rail 底部 + hero 剪影）、阴阳玉（当前筛选前缀）、五瓣樱（区块头）、扇面（次级区块头）、注连绳（分组分隔）、竖排「博麗神社」。其中鸟居两处与竖排只在神社档出现，见下方三档差量表。 5作品卡的信息层级：标题压在图上但走常驻深色遮罩（不是 hover 才有）。原设计的「点赞/浏览」两枚数已删 —— 三站只有 Safebooru 给 fav_count，yande.re 的 JSON 实测 44 个键不含它、Gelbooru 字段表里也没有；把"不知道"当 0 会把整站系统性压到最低档。现在摆的是三站都给的分数（GalleryPost.score）。 6详情浮层 340 覆盖式，内容区不重排 —— 上一版量过：并排会把每列压到 148，违反 200 预算。

为什么这版不含漫画块

按你的口径：漫画不是辅区，是另开一屏。所以首页 100% 图库，rail 保留漫画域入口但不占内容位。附带一条实现上的好处：图库这条链在代码里对 JS 引擎零引用（gallery/ 下 grep VeneraJsEngine|JsComicSource 空命中，取数走 GelbooruClient.kt / PixivClient.kt / DanbooruArtistClient.kt 直连），所以这版首页不依赖 GraalJS——移植里最贵最不确定的一环从首屏关键路径上摘掉了。

隔离口径同时守住：首页块由图库侧提供，壳层只认 slot 接口，漫画侧将来接同一个 slot，两边不互相 import。

参考图里我拒绝照抄的（CRITICAL 级）

文字直接压在插画上：改为遮罩常驻，正文对比度守 4.5:1（本稿标题 #FFF / 遮罩后 ≈ #1A1622 底）。 选中态靠一条紫渐变：渐变保留做质感，但选中语义仍由 3px 指示条 + 字重承担，键盘与读屏能解释。 圆角 12–16 到处用：容器与控件守 Fluent（卡 8 / 控件 4），只有插画卡允许 12。 整页半透明毛玻璃压在壁纸上：系统 Mica 实测画不出来（S0-6a 判负），整页模糊只会得到一片糊；背景画只进 hero。 粉色细描边当边界：描边一律中性 #353535，色彩只承担强调不承担边界。 轮播自动播放：桌面鼠标环境禁自动播，只留左右键与分页点（也与既有"轮播不做真 3D、2 分钟节流"一致）。

素材红线

本稿所有插画位都是占位色块 + 自绘矢量纹样。东方 Project 的官方立绘、以及参考图里那种 AI 生成的角色图都不能进产品素材；可用的是语汇（鸟居、阴阳玉、五瓣樱、注连绳、扇面、弹幕点阵、和色、竖排汉字）。背景画要么走"用户本地自备并导入"，要么委托原创。
