「某些 JM 漫画详情页预览裂成横条」的根因不是解码器，而是**同一个「混淆块数」在本仓库存在多份口径 + 还原几何算错**。2026-09-22 按权威口径对齐 `pictureName`；2026-09-23 用户回报「还是会有这种重复+条纹」，据此定位到下面第三类成因（块边界漂移）。**两类修复都还只有编译/装机过，真机未验证**（2026-09-23 一加真机整天没连，只有 emulator-5554）。

**Why:** 镜像外部脚本的算法时，任何"等价改写"都可能不等价 —— Kotlin 那份用 `substring(0, lastDot)` 取 `pictureName`，jm.js 是**无条件砍掉整条 URL 末尾 5 个字符**（不是去扩展名）。`.webp`（含点正好 5 字符）两种切法等价，`.jpg`/`.png` 会多砍一位数字 → MD5 入参不同 → 块数不同 → 还原按错的边界重排。分叉概率实测：epId>421926 段 86.7%、`%10` 段 89.1%；只有 ≥268850 且走 MD5 的漫画才受害，所以观感是"有些漫画"。

**How to apply:**
- 任何 JM 图像还原逻辑以 `assets/sources/jm.js`（`onImageLoad` 里的 `const num` + `modifyImage`）为**唯一权威口径**，Kotlin 侧要逐字同串，别"等价改写"（同族规则见 [[feedback-mirror-official-values]]、[[project-js-source-assets-not-live]]）。
- **结构性事实**：详情页预览那批 URL **从不走** `comic.onImageLoad`，只拿得到「URL 推导」的块数；阅读器与下载才会拿到 JS 的权威值。所以「只有预览受害、阅读器正常」是符合预期的诊断指纹，不是巧合。
- **公开纠正一条我给过的错误推论**：我说过"先看预览会污染阅读器那一页"。查过 key 构造后确认**不成立** —— 阅读器用 `ComicPageSource.cacheKey`（`sourceKey@comicId@epId@imageKey`），预览用 URL 串，两套 key 不重叠，最多各解码一次。判断"两份数据会不会互相锁死"要先去读 key 是怎么拼的。
- **排障指纹**：`adb logcat -s ImagePipeline:W` 出现「JM 块数分叉」= 还存在第三份口径，或 jm.js 又改了算法。没出现就仍是同一份。
- **条状 = 两个可判别形状**：同一症状既可能是"块数算错"（切在错边界），也可能是"**根本没还原**"（还原被静默跳过）。后者 2026-09-22 由一次性能优化引入过：`decodeAndDescramble` 返回 null 时旧写法直接往下走、把未还原字节交给 Coil 原样解码 —— 还顺带按 `cacheKeyFor` 把错图锁进内存缓存。日志里新增的「JM 去混淆失败」哨兵专指这一类。
- **第三个独立成因（2026-09-23 定位并修）**：块边界**漂移**。服务端按**原图高**切块，而 `decodeAndDescramble` 在 `inSampleSize>1` 时拿**降采样后的高**重新 `floor(h/n)` 推导边界，每次 floor 的余量逐块累加。仿真 108 组 (H,n,s) 里 **53 组漂移 ≥ 块高 5%**，最坏 `H=1280 n=18 s=8` 漂 14px 而块高才 8px（**175%**，等于整块画到别处 → 看着像"重复"）。这解释了为什么**同一本里有的预览干净、有的裂条**（干净那页恰好整除），也解释了为什么阅读器（盒子大 → sample=1）永远正常。修法：边界一律按原图高算再线性映射到位图实际高（`(y*h)/H`），误差钉在 1px 内；调用方必须把 `inJustDecodeBounds` 那份 `outHeight` 传进来。
- ⚠️ 原先 `sampleSizeFor` 那条「漂移不超过块高 1/8」的论证是**错的**（只保证块 ≥8px，没约束累加漂移），别照它再推一次。
- **验证口径**：同一本 `.jpg` 的 JM 漫画，预览第 1 张应与阅读器第 1 页完全一致；且**同一本里不该再有"第 2 张干净、第 1/3 张裂条"这种按页分布的差异** —— 按页分布就是边界漂移，整本一致地裂才是块数算错。用户回报时按这条分辨，别一上来又改块数算法。
- **收藏原画落盘（2026-09-23 用户拍板）**：`favorite_images.local_path` 对网络页此前恒为空（S7 方案写了「原画落盘」但只对本地漫画页成立），所以收藏墙加载的是没去混淆的原图。现在收藏时以 `Size.ORIGINAL` 取那一页解好混淆的位图写进 `filesDir/favorite_images/`。**给了三个选项（只落盘 / 落盘+旧条目渲染期自愈 / 只做渲染期反混淆），用户选「只落盘」** → 旧条目不做自愈：漂移修好后它们显示是对的，只是仍受签名地址过期与离线影响。别把自愈当顺手优化重新提。

**2026-09-29 真机新增的三条数据面事实**（读数来自 `ReaderPageLoad` 日志，禁漫 ep=1467503 全本每页失败）：

- **JM 正文页现在发的是 `.webp`**（`…/media/photos/1467503/00009.webp`），不再是 `.jpg`。块数判据只排除了
  `.gif`，所以 webp 一律走 MD5 推导（同一章实测出现 4 / 8 / 10 / 14 多档）。
  ⚠️ **仍待真机判读**：把下面那条压缩障碍清掉之后，"webp 到底该不该去混淆、块数对不对"没验过 ——
  如果出图但**横条错位/撕裂**，那是这一条，**别再回去动 gzip 那处**。分辨口径沿用上面那条：
  整本一致地裂=块数算错，按页分布=边界漂移。
- **新 CDN 域名段没进枚举表**：失败主机是 `cdn-msp2.jmapiproxy1.cc`；表里有 `jmapic` 而没有 `jmapi`，
  它只靠"路径含 `/media/photos/` 且 host 含 `cdn-msp`"那条兜底才被认成 JM 混淆图。
  ⇒ 站方换域名时**兜底那半截才是真在干活的**，别以为枚举表覆盖住了。
- 这一次"全本每页去混淆失败"**既不是块数也不是边界**：字节是 gzip 压缩流（首 4 字节 `1f8b08`）、
  `inJustDecodeBounds` 读出 `-1x-1`，`BitmapFactory` 根本没解出图。机制见
  [[project-coil-image-pipeline-facts]] 里 `Accept-Encoding` 那条。
  **教训**：「JM 去混淆失败」这句哨兵涵盖的成因不止"还原被跳过/算错"，还包括"字节不可解"；
  所以失败文案必须自带**魔数 + 读出尺寸 + 每块高**，否则又得从零猜一轮（本轮靠这三项一次定死）。
